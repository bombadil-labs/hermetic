For TypeScript and JavaScript: an ESLint plugin and a runtime check

Hermetic functions

A hermetic function reads nothing but its inputs: its arguments, including this. It doesn't use imports, module-level variables or globals, not even built-ins such as Math. Anything it needs has to be passed in, so all of its dependencies are visible in its inputs.

npm install --save-dev @bombadil/eslint-plugin-hermetic Read the case studies GitHub

Inputs, including this

Every value a function reads is one of its inputs, whether or not it appears in the parameter list. A function that reads a module-level variable or calls fetch has inputs its signature doesn't show. The hermetic/sealed rule reports every such input in a hermetic function: an import, a module-level variable, a global like fetch, or a built-in like Math.

Built-ins are inputs too: which ones exist, and what they do, depends on the runtime and on any code that replaced them. The code that binds a hermetic function passes in the ones it needs, and intrinsics picks the deterministic ones out of the runtime. undefined, NaN and Infinity can't be changed, so they read like keywords.

this is an input like the others: an implicit first argument. .call passes it explicitly, and .bind fixes it in advance, which is partial application. That makes this a convenient place for dependencies: bind them once, and pass the other arguments at each call. TypeScript type-checks the value of this in every .call, .apply and .bind.

The essay Thinking Like a Function explains this way of looking at functions in more depth.

Hermetic doesn't mean pure. A hermetic function can still change its inputs, or call methods on them that do I/O. Purity can't be checked in JavaScript, because any input can be a Proxy. Whether a function reads anything besides its inputs can be checked, with the same scope analysis ESLint uses to find undefined variables.

It isn't a sandbox either. Every value, even a literal, leads through its prototype chain to built-ins the whole program shares, and a hermetic function can still change them: ({}).__proto__.hasOwnProperty = () => true changes hasOwnProperty for every object. The rule checks names, not where values lead. To run a function you don't trust, use confine: it runs the function in a Hardened JS compartment, where the shared built-ins are frozen and the global object is empty. 

function applyDiscount(this: Pricing, invoice: Invoice) {
  "use hermetic";
  const discounted = invoice.total * (1 - this.rate);
  return { ...invoice, total: this.clamp(discounted) };
}

// Supply the dependencies once, by binding this.
const pricing = { rate: config.rate, clamp: toCents };
export const applyPricing = applyDiscount.bind(pricing);

What you get

Portable code

The function's source is all of its behavior, so it runs the same in another file, a worker or a sandbox: new Function("return " + fn.toString())() behaves exactly like fn.

Tests without module mocks

Pass test values as inputs instead of mocking modules. Wrap this in a Proxy to record every use of the dependencies the function was given.

Dependencies you can find

To find out which functions can call Stripe, look at the code that passes the Stripe client in.

Self-contained changes

A function's inputs, the type of this and its body are everything a person or an agent needs to read before changing it.

Check and confine at runtime

A hermetic function's source is all of its behavior, so it can be stored, sent and run somewhere else. @bombadil/hermetic checks it there, without ESLint. check parses a function's source and reports everything it reads besides its inputs. confine runs a hermetic function in a Hardened JS compartment, where the shared built-ins are frozen, the clock and random numbers throw unless they are passed in, and the global object is empty.

On the {{crosscheck.functions}} functions and methods in the published JavaScript of Effect, RxJS and TanStack Query, check reports exactly what hermetic/sealed reports, at the same places, every one. So lint functions where they are written, and check them where they arrive.

The checker is hermetic itself. Its parser comes in through this, and it reads no globals, so its own source can be sent to another runtime and bound there, and it passes its own check. The package's README covers both functions. 

npm install @bombadil/hermetic
import "ses";
lockdown(); // once, at startup: the application's decision

import { check, confine } from "@bombadil/hermetic";

check(source);
// { form: "function", marked: true, hermetic: false,
//   problems: [{ kind: "freeVariable", name: "rate", … }] }

// A HermeticError, unless it is hermetic:
const area = confine(source);
area.call(harden({ width: 2, height: 3 }));

Make existing code hermetic

hermetic/prefer-hermetic finds functions that are already hermetic and marks them. With the lift option, it also rewrites functions that read module-level values or globals. The body moves into a new hermetic function that receives those values through this, and the original function becomes a wrapper that passes them in. Its name, signature and export stay the same, so callers don't change.

Removing the cost at build time

A lifted function makes one extra call and a few property reads each time it runs. unlift reverses the rewrite exactly, turning each wrapper back into the original function, so the source can stay hermetic while the build runs the original code.

In the table, the unlifted source performs like the second copy of the original, so the remaining difference is noise. Unlifting the lifted code gives back the original program in every file, and Effect's {{effect.suite.unlifted.passed}} tests pass on the unlifted source too. unlift isn't part of the published package yet; a bundler plugin that runs it on production builds is next.

Get started

Install the plugin next to typescript-eslint and add the recommended config. Mark a function with a "use hermetic" directive or an @hermetic JSDoc tag. The rule only checks marked functions, so turning it on doesn't affect the rest of your code.

Documentation: hermetic/sealed, hermetic/prefer-hermetic, passing built-ins in, and check and confine.

Up to 0.2.0, the plugin was published as @bombadil/hermetic, which is now the runtime package. If your config imports it, install @bombadil/eslint-plugin-hermetic and change the import. From 0.3.0, hermetic functions read no globals, so the ground and aliasing settings are gone, and methods can't be hermetic yet. 

// eslint.config.js
import { defineConfig } from "eslint/config";
import tseslint from "typescript-eslint";
import hermetic from "@bombadil/eslint-plugin-hermetic";

export default defineConfig(
  ...tseslint.configs.recommended,
  hermetic.configs.recommended,
);
