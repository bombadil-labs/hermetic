An ESLint plugin for TypeScript and JavaScript

Hermetic functions

A hermetic function depends only on what it is handed: its arguments, this, and a small, explicit ground of harmless globals. It may still mutate and cause effects, but only through what it was handed. So everything it can touch is visible at the call.

npm install --save-dev @bombadil/hermetic Read the case studies GitHub

Two doors

A hermetic function's whole world arrives through its arguments and this. The rule, hermetic/sealed, reports everything else it reaches for: a module constant, an import, a global, Math.random.

Authority is granted in a thin binding layer, ordinary code that builds this and applies it. TypeScript already checks it: a this parameter is typed at every .call, .apply and .bind.

Hermetic is not pure. Purity cannot be enforced in JavaScript: any argument can be a Proxy, or carry a getter that does I/O. Hermeticity can. "No free variables" is a syntactic fact that ESLint's scope analysis already computes. 

function applyDiscount(this: PricingCtx, invoice: Invoice): Invoice {
  "use hermetic";
  return { ...invoice, total: this.clamp(invoice.total * (1 - this.rate)) };
}

// The binding layer: the one place authority is granted.
const pricing: PricingCtx = { rate: config.discountRate, clamp: clampToCents };
export const applyPricing = applyDiscount.bind(pricing);

What two doors buy you

Anything standing at the doors sees everything the function can do.

Relocation

Move it to another file, a worker or a realm, unchanged. The acid test: new Function("return " + fn.toString())() behaves identically to fn.

Mocks, traces, replays

Wrap this in a Proxy and you log every use of the authority the function was granted, with no instrumentation inside it.

Authority audits

Every grant lives in the binding layer, so "what can touch Stripe?" is answered by reading the wiring.

Context-complete units

Arguments, the this type and the body are everything an agent or a reviewer needs to change the function safely.

Make a codebase hermetic in one command

hermetic/prefer-hermetic marks the functions that are hermetic already. With lift, it splits the rest: the body moves into a hermetic core, and the original name becomes a binding that hands the core exactly what it used to take from its surroundings. Callers do not change. 

npx eslint --fix --rule '{"hermetic/prefer-hermetic": ["warn", {"lift": true}]}' src/

The fix applies only where the split cannot change behavior or types, and leaves the rest, with a reason, for a person. On Effect, the library's own test suite passes on its lifted source: {{effect.suite.lifted.passed}} tests, {{effect.suite.lifted.failed}} failures.

Checked in the source, erased in the build

A lifted function costs one more call and a few property reads each time it runs. The lift has an exact inverse, unlift, which folds every binding back into the function it came from. The source stays hermetic, checked and testable; the build ships the original code.

Unlifting the lifted corpus gives back the original program in every file, and Effect's {{effect.suite.unlifted.passed}} tests pass on its unlifted source too.

Get started

Install the plugin next to typescript-eslint, add the recommended config, and mark a function with a "use hermetic" directive or an @hermetic JSDoc tag. The rule checks only marked functions, so it is safe to enable everywhere.

Read about hermetic/sealed, hermetic/prefer-hermetic, and configuring the ground. 

// eslint.config.js
import { defineConfig } from "eslint/config";
import tseslint from "typescript-eslint";
import hermetic from "@bombadil/hermetic";

export default defineConfig(
  ...tseslint.configs.recommended,
  hermetic.configs.recommended,
);
